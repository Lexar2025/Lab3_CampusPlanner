# Дизайн ЛР №7: серверные задачи и TanStack Query

**Проект:** `Lab3_CampusPlanner` (Expo SDK 57, Expo Router `~57.0.31`, React Native `0.86.3`, TypeScript)
**Дата:** 2026-11-25
**Источники требований:** `lab-07-server-state-react-query.md`, `API.md`
**База:** завершённая ЛР №6 (ветка `Lab6`, коммит `1af9c3d`)

---

## 1. Цель и зачем это делается

Перенести задачи авторизованного пользователя с локального `TasksContext` на учебный REST API и сделать серверное состояние управляемым через TanStack Query. После входа пользователь должен видеть свои задачи с сервера, создавать, редактировать, менять статус и удалять их, а также видеть загрузку, ошибку, пустой список и обновление данных.

Дополнительно требуется:

- серверная фильтрация списка по статусу (`GET /tasks?status=active|completed`) с фильтром в `queryKey`;
- сохранить привычное поведение ЛР №1–ЛР №6: подтверждение удаления, отмену удаления, подсветку новой задачи, поиск, статистику, свайпы, черновик формы и тему.

## 2. Цели

- Все HTTP-запросы к задачам живут в отдельных API-модулях, а не в экранах.
- Список и детали получают данные через `useQuery`; создание, изменение, смена статуса и удаление — через `useMutation`.
- Ключи запросов учитывают `user.id`; фильтр статуса входит в ключ списка.
- После мутаций кэш становится актуальным через инвалидацию.
- На экране списка есть первая загрузка, ошибка с повтором, пустой список, pull-to-refresh.
- При `401` пользователь выходит из сессии и кэш очищается; сеть, `400`, `404`, `500` не завершают сессию.
- Массив серверных задач не дублируется в React Context.

## 3. Не-цели

- Регистрация, смена пароля, refresh token, серверный logout — Campus API их не поддерживает.
- Офлайн-режим и очередь отложенных запросов на уровне всего приложения.
- Серверный поиск `q`: поиск остаётся локальным (см. раздел 4).
- Оптимистичные мутации создания/редактирования с ручным откатом: для них достаточно инвалидации и состояния отправки.

## 4. Анти-цели

- `new QueryClient()` внутри компонента — кэш будет уничтожаться на каждом рендере.
- Сброс сессии при любой ошибке запроса, а не только при `401`.
- Хранение токена или пароля в `AsyncStorage`, `.env`, параметрах маршрута или логах.
- Возврат локального `INITIAL_TASKS` после выхода: пользователь не должен видеть чужие демо-задачи.
- Показ карточки, которая уже удаляется, и повторная отправка `DELETE` по ней.

## 5. Контракт API и ограничения

- Базовый URL — тот же `EXPO_PUBLIC_API_URL`, что в ЛР №6.
- Все запросы к задачам требуют `Authorization: Bearer <accessToken>`.
- `GET /tasks` возвращает `{ items: Task[] }`; поддерживает `status=active|completed`.
- `GET /tasks/:id`, `POST /tasks`, `PATCH /tasks/:id` возвращают `{ item: Task }`.
- `POST` и `PATCH` отвечают `200`, а не `201`; проверка строится по `response.ok`.
- `DELETE /tasks/:id` отвечает `204` без тела: нельзя вызывать `response.json()`.
- Модель задачи: `dueDate: string | null` в формате `YYYY-MM-DD`, появился `updatedAt: string`.
- `title` — до 120 символов, `subject` — до 80; сервер обрезает пробелы по краям.
- `q` ограничен 48 байтами UTF-8 и использует SQL `LIKE`; для кириллицы регистрозависим. Поэтому серверный поиск не используем.
- `404` на задаче означает «нет задачи или она чужая» — это не повод выходить из сессии.
- `401` на защищённом маршруте означает недействительную сессию — нужен выход.

## 6. Подходы и выбор

### 6.1. Источник данных

1. **Оставить `TasksContext` и синхронизировать его с сервером вручную (отклонено).**
   Пришлось бы вручную хранить `isLoading`, `error`, инвалидацию, повторы и гонки. Это дублирует TanStack Query и нарушает требование о единственном источнике серверного состояния.
2. **TanStack Query как единственный источник серверных задач (выбрано).**
   `useQuery` отвечает за список и детали, `useMutation` — за изменения, `invalidateQueries` — за согласованность. Context остаётся только для UI-состояния: подсветка новой задачи и отложенное удаление.

### 6.2. Фильтрация и поиск

1. **Всё локально (не выбрано).** Просто, но не закрывает дополнительное задание.
2. **Статус на сервере + поиск локально (выбрано).**
   `GET /tasks?status=active|completed` показывает серверную фильтрацию и попадает в `queryKey`. Поиск остаётся мгновенным и не упирается в 48-байтный лимит `q`. Статистика считается по отдельному запросу без фильтра.
3. **Статус и поиск на сервере (отклонено).**
   Поиск стал бы сетевым, с задержкой, лимитом длины и особенностями регистра; для учебного списка это ухудшение UX без пользы.

### 6.3. Удаление с отменой

1. **Немедленный `DELETE`, отмена через повторное создание (отклонено).**
   Восстановление даёт новый `id`, может создать дубликат и плохо сочетается с ошибками сети.
2. **Немедленный `DELETE`, без отмены (отклонено).**
   Теряется привычный сценарий ЛР №1–ЛР №5, пользователь просил сохранить функционал.
3. **Отложенный `DELETE` (выбрано).**
   По подтверждению карточка сразу исчезает из списка и статистики, но остаётся на сервере. В течение 5 секунд видна плашка «Удаление… Отменить». Если нажать «Отменить», таймер снимается, карточка возвращается без запроса к серверу. Если таймер истёк, уходит `DELETE`; при успехе кэш инвалидируется, при ошибке карточка возвращается и показывается сообщение.

### 6.4. Где живёт отложенное удаление

1. **Внутри экрана списка (отклонено).**
   При переходе в детали или настройки экран остаётся в стеке, но при выходе из аккаунта таймеры теряются вместе с компонентом. Логика удаления размазывается по экрану.
2. **Провайдер `TasksUiProvider` внутри `(app)` (выбрано).**
   Провайдер живёт всё время авторизованной сессии, переживает переходы между экранами, хранит таймеры, список удаляемых `id` и `lastCreatedId`. При размонтировании (выход из аккаунта) отложенные удаления досылаются с сохранённым токеном, насколько позволяет сеть.

## 7. Архитектура

### 7.1. Поток данных

```text
Экран
  → useTasksQuery / useTaskQuery        (чтение)
  → useCreateTask / useUpdateTask       (изменение)
  → TasksUiProvider.scheduleDelete      (удаление с отсрочкой)
```

## 8. Детали реализации

### 8.1. Типы

```ts
export interface Task {
  id: string;
  title: string;
  subject: string;
  priority: TaskPriority;
  status: TaskStatus;
  dueDate: string | null;
  createdAt: string;
  updatedAt: string;
}

export interface CreateTaskInput {
  title: string;
  subject: string;
  priority: TaskPriority;
  status?: TaskStatus;
  dueDate?: string | null;
}

export type UpdateTaskInput = Partial<CreateTaskInput>;
```

`TaskStatusFilter = 'all' | TaskStatus` остаётся UI-типом.

### 8.2. API-клиент

`apiRequest<T>(path, token, init?, onUnauthorized?)`:

- вызывает `authorizedFetch` из ЛР №6;
- сетевую ошибку заворачивает в `ApiError` со `status: null` и текстом про интернет;
- при `!response.ok` бросает `ApiError` с сообщением сервера и статусом;
- при `204` возвращает `undefined`;
- иначе разбирает JSON; битый JSON — понятная ошибка.

`tasks.ts` не собирает URL в экранах. Идентификатор кодируется через `encodeURIComponent`. `getTasks` принимает `TaskListParams` и формирует `?status=...` через `URLSearchParams`. `deleteTask` возвращает `Promise<void>`.

### 8.3. Ключи и запросы

```ts
taskKeys.all(userId)              // ['tasks', userId]
taskKeys.lists(userId)            // ['tasks', userId, 'list']
taskKeys.list(userId, status)     // ['tasks', userId, 'list', { status }]
taskKeys.detail(userId, id)       // ['tasks', userId, 'detail', id]
```

- `useTasksQuery(filter)` — список; `enabled: Boolean(user && accessToken)`; `placeholderData: keepPreviousData`, чтобы смена фильтра не мигала пустым экраном.
- `useAllTasksQuery()` — тот же ключ `list(userId, 'all')`, нужен для статистики при активном фильтре. При фильтре «Все» оба хука используют один кэш и один запрос.
- `useTaskQuery(id)` — детали; `enabled` требует `id`, пользователя и токен.
- В ключ не попадает токен.
- Политика повторов задаётся только для запросов: не повторять `4xx`, один повтор для сети и `5xx`. Мутации не повторяются (`retry: 0`), потому что `POST /tasks` не идемпотентен и повтор после таймаута создал бы дубликат.

### 8.4. Мутации

- `useCreateTask`: `POST /tasks`, при успехе инвалидирует `taskKeys.all(user.id)`.
- `useUpdateTask`: `PATCH /tasks/:id`, при успехе инвалидирует `taskKeys.all(user.id)`; используется для редактирования.
- `useToggleTaskStatus`: отдельная мутация для чекбокса и свайпа. Оптимистично меняет статус во всех кэшах списков и в кэше деталей, при ошибке откатывает снимок, в `onSettled` инвалидирует. Пока мутация в полёте, повторный свайп или тап по карточке игнорируется, чтобы не отправлять противоречивые `PATCH`.
- Удаление выполняет `TasksUiProvider` через собственный `useMutation`, потому что таймер живёт вне экрана.
- В экранах при `401` ошибка не показывается: сессия уже завершается, guard переключает группу.
- Для остальных ошибок показывается `Alert` или inline-ошибка с текстом `ApiError`.

### 8.5. Отложенное удаление

- `DELETE_DELAY_MS = 5000`.
- `scheduleDelete(task)` игнорирует повторный вызов для того же `id`.
- Карточка исчезает сразу, потому что список и статистика фильтруют `pendingIds`.
- Плашка внизу показывает факт ожидания: «Удаление… Отменить». Отмена снимает таймер и возвращает карточку без сети.
- По истечении таймера уходит `DELETE`. Успех: удалить задачу из кэшей списков, убрать кэш деталей, инвалидировать `taskKeys.all(user.id)`. Ошибка: убрать `id` из `pendingIds` (карточка возвращается) и показать сообщение; при `401` — выход без лишнего `Alert`.
- Поддерживается несколько одновременных удалений: `Map<id, timer>`; плашка отменяет последнее. Все остальные таймеры доживают до `DELETE`.
- При размонтировании провайдера таймеры снимаются, а отложенные удаления досылаются напрямую с сохранённым токеном. Это покрывает выход из аккаунта; при убийстве процесса задача останется на сервере и появится при следующем запуске. Ограничение честно фиксируется в отчёте.

### 8.6. Сессия и кэш

- `AuthContext.signIn` после успешного входа очищает кэш, чтобы данные прошлого пользователя не могли просочиться.
- `clearSessionOn401` и `signOut` вызывают `queryClient.clear()`.
- `authorizedFetch` по-прежнему вызывает `onUnauthorized` только при `401`; `apiRequest` передаёт туда `signOut`.
- После `401` запросы не повторяются, guard монтирует `(auth)`.

### 8.7. Экран списка

- Первая загрузка — центрированный `ActivityIndicator`.
- Ошибка без данных — `EmptyState` с кнопкой «Повторить».
- Ошибка при наличии данных — компактная плашка с повтором, список остаётся.
- Пусто: нет задач вообще / пусто после фильтра / ничего не найдено по поиску — разные тексты, как в ЛР №5.
- `RefreshControl` вызывает `refetch` списка и статистики.
- Сортировка по приоритету, поиск и статистика остаются прежними; статистика считается по полному списку без удаляемых задач.
- Состояние фильтра и поиска живёт в `TasksUiProvider`, чтобы после создания сбросить их на «Все» и пустой поиск: новая задача должна быть видна, даже если текущий фильтр или поиск её исключают.
- Удаление из свайпа и из раскрытой карточки проходит через подтверждение и `scheduleDelete` (сейчас кнопка в карточке удаляет без подтверждения — это исправляется).

### 8.8. Формы и даты

- `TaskForm` принимает `submitting` и `errorMessage`; кнопка показывает «Сохранение…» и блокируется.
- Дата вводится как `ГГГГ-ММ-ДД`, проверяется регуляркой и календарём (например, `2026-02-31` отклоняется). В API уходит `YYYY-MM-DD` или `null`, а не ISO-строка.
- `AppInput` получает `maxLength`: 120 для названия, 80 для предмета.
- `parseDateOnly` и `formatDateOnly` разбирают дату как локальную, без сдвига на предыдущий день в отрицательных часовых поясах.
- `isTaskOverdue` сравнивает срок с концом текущего дня.
- Ключ черновика создания делается персональным: `@campus_planner/create_draft:${user.id}`. Старый общий ключ удаляется при первом чтении. Следующий пользователь не увидит чужой черновик, а черновик того же пользователя переживёт повторный вход.

### 8.9. Детали и редактирование

- Детали: загрузка, ошибка с повтором, `404` → «Задача не найдена», кнопки блокируются на время смены статуса.
- Удаление из деталей: подтверждение → `scheduleDelete` → `router.back()`; плашка отмены видна на списке.
- Редактирование: если задача ещё грузится — спиннер; если не найдена — `EmptyState`; сохранение показывает «Сохранение…», после успеха `router.back()`.
- После создания сначала вызывается `markCreated(task.id)` и `resetListView()` (фильтр «Все», пустой поиск), затем `router.back()`. Экран списка ждёт, пока задача появится в данных после инвалидации, и только тогда запускает подсветку; `clearLastCreated` срабатывает по таймеру примерно через 1,2 секунды после появления карточки. Если задача так и не появилась, `lastCreatedId` живёт до следующего создания или выхода.

## 9. Состояния и поведение

| Ситуация | Поведение |
|---|---|
| Первая загрузка списка | Спиннер по центру |
| Ошибка сети/500 без данных | EmptyState + «Повторить» |
| Ошибка обновления при данных | Плашка, список остаётся |
| Пустой ответ сервера | «Задач пока нет» + «Добавить» |
| Пусто после фильтра | «В этой категории пусто» |
| Поиск ничего не нашёл | «Ничего не найдено» |
| Pull-to-refresh | `RefreshControl`, обновляет список и статистику |
| Создание | «Сохранение…», кнопка заблокирована |
| Редактирование | «Сохранение…», кнопка заблокирована |
| Смена статуса | Оптимистично, с откатом при ошибке и инвалидацией |
| Удаление | Карточка скрыта, 5 с «Удаление… Отменить», затем DELETE |
| Отмена удаления | Карточка возвращается, сервер не тронут |
| Ошибка DELETE | Карточка возвращается + сообщение |
| 401 | Выход, очистка кэша, экран входа |
| 400/404/500 | Сообщение, сессия сохраняется |

- `npx expo export --platform android`;
- smoke-тесты API: `GET /tasks` без токена → `401`, с токеном → `200`; создание → `200`; `PATCH` → `200`; `DELETE` → `204`; повторный `GET` → `404`.

Ручная проверка на устройстве/эмуляторе (если доступен):

1. Вход, список с сервера, у нового пользователя пусто.
2. Создание, перезапуск приложения, задача на месте.
3. Редактирование, изменение статуса, статистика.
4. Фильтр «Активные»/«Выполненные» — в запросе есть `status`, ключ кэша меняется.
5. Поиск, пустой результат, pull-to-refresh.
6. Удаление: карточка исчезает, отмена возвращает, повторное удаление без отмены исчезает после перезапуска.
7. Авиарежим: ошибка и повтор, сессия не сбрасывается.
8. Просроченный/недействительный токен: выход и очистка кэша.
9. Выход и вход другим пользователем: чужих задач нет.
10. Прямой переход на `/task/:id`: детали загружаются с сервера.

Ограничение окружения: если нет `adb`/эмулятора, ручной прогон остаётся за пользователем; это будет отмечено как незакрытый шаг, а не как «всё проверено».

## 11. Что остаётся на усмотрение реализатора

- Точные тексты ошибок и пустых состояний.
- Нужен ли компактный баннер ошибки при наличии данных или достаточно `Alert`.
- Форма хранения `pendingIds` (`Map` + версия или `Set` в состоянии).
- Добавлять ли `updatedAt` в экран деталей.
- Стили плашки «Удаление… Отменить» в рамках текущей темы.

## 12. Принятые решения

- Серверный фильтр — только `status`; поиск локальный.
- Удаление отложенное на 5 секунд, карточка сразу скрывается.
- Отмена удаления не ходит в сеть.
- `TasksContext` удаляется; UI-состояние переносится в `TasksUiProvider`.
- Статистика считается по отдельному запросу без фильтра.
- Кэш очищается при входе, выходе и `401`.
- Демо-данные `INITIAL_TASKS` удаляются.
- После создания фильтр сбрасывается на «Все», поиск очищается; подсветка ждёт появления задачи в данных.
- Черновик создания привязан к `user.id`, старый общий ключ удаляется.
- Повторы включены только для запросов; мутации не повторяются.
- Смена статуса оптимистичная; редактирование — через инвалидацию после успеха.
- Фильтр и поиск хранятся в `TasksUiProvider`, чтобы создание могло вернуть список в видимое состояние.
